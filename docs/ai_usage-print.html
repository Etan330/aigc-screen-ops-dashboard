第一轮：产品原型开发

这一轮我把测评题目重新组织成一份可直接执行的需求，明确了业务场景、指标口径、异常规则、数据要求和交付边界。关键段落如下：

业务场景：某品牌已上线多台 AIGC 互动大屏……完整链路为「用户参与 → 发起 AI 生成 → 生成成功或失败 → 内容安全审核 → 结果展示 → 用户扫码或分享」。运营人员需要同时管理活动效果、AI 服务质量、设备运行状态三个方面。

核心指标：参与人数、AI 生成成功率、扫码转化率、分享转化率、平均生成时长、内容审核通过率、设备在线率。KPI 卡片除了数值，还应展示必要的业务上下文，例如分子与分母、与上一可比周期的变化或异常状态，避免只有一个孤立百分比。

口径要求：优先从同一套原始模拟数据派生指标，不要为不同图表分别写死结果。生成成功率的分母只含成功与失败，进行中任务不计入；审核通过率的分母只含通过与拒绝，待审核不计入；扫码与分享转化率按内容去重，同一内容多次扫码或分享只计一次。默认把「生成成功且审核通过」的内容定义为可扫码、可分享的有效内容。请处理好分母为零、跨点位用户去重、跨日期任务、审核待处理等边界情况。

漏斗要求：涉及漏斗时应统一统计对象和去重口径，不能将人数、任务次数、内容数混合计算为同一条转化漏斗。

异常规则（演示阈值）：生成成功率低于 90% 且该点位当日已完成生成尝试不少于 20 次；平均生成时长超过 15 秒且当日成功任务不少于 20 次；内容审核拒绝率超过 10% 且已审核内容不少于 20 条；设备最近一次心跳距模拟数据基准时间超过 5 分钟判为离线。以上阈值属于演示规则，应清晰标注，方便后续修改。

异常展示要求：每条异常应展示异常类型、严重程度、发生日期、涉及点位或设备、实际指标、阈值及样本量、可能的原因（明确属于待验证假设）、运营建议及下一步排查方向。不要只用静态红色标签假装实现异常监控，异常必须根据模拟数据和规则动态计算。

数据要求：6–8 个运营点位、10–15 台设备、最近 30 天业务数据，优先采用事件级模拟数据。模拟数据必须有确定的随机种子，可以复现；同一指标在不同图表、详情页中计算结果应一致；异常需要在原始数据中有对应证据，不能只在 UI 上编造；数据不得使用真实用户隐私信息；明确统计截止时间。

交付要求：React + Vite + TypeScript，Recharts 用于图表，lucide-react 用于图标，使用本地 JSON 模拟数据。README 面向没有开发经验的 macOS 用户；METRICS 一页以内；AI_USAGE 说明 AI 使用情况。完成开发后请实际执行安装、构建及必要的功能验证，修复可以发现的问题，不要将明显报错的项目直接作为交付物。

边界：不允许以静态截图、设计稿、伪代码代替可运行产品；不允许为了视觉表现捏造与原始数据不一致的指标；不得虚构已经完成的测试、人工修改或项目部署。请先在内部完成业务模型、指标口径、数据结构及页面架构的设计，再进行编码。最后输出项目目录、运行方法、完成的功能、实际测试结果和未完成事项。

四、我完成的主要修改与判断

4.1 由我提出并决定的内容

1）业务目标与交付形态

- 我确定了要交付的是可直接打开使用的在线看板，而不是代码仓库或本地项目，因此选择 GitHub Pages 静态部署； - 我判断不需要引入后端，因为测评场景下数据是模拟的、指标口径是固定的，纯前端已经足够，也能保证招聘方打开即可使用； - 我在第二轮明确要求「不重新开发」，保留第一版的产品形态，只做部署与交付整理——理由是第一版已经通过了我自己的验收，重做只会带来风险而不带来收益。

2）指标口径与边界

题目已经给出了核心口径要求。我的补充是把它们写清楚、写死，并要求实现时严格遵守：

- 生成成功率分母只含成功与失败，进行中任务不计入； - 审核通过率分母只含通过与拒绝，待审核不计入； - 扫码与分享按内容去重，同一内容多次行为只计一次； - 「生成成功且审核通过」才是有资格被扫码 / 分享的有效内容，审核拒绝的内容不进入转化率分母； - 明确时间归属：参与与生成按事件自身日期，内容 / 审核 / 扫码 / 分享统一归因到内容生成日，保证四步口径可比； - 分母为零时显示「—」而不是 0 或 NaN； - 所有指标必须从同一套原始数据派生，不允许为不同图表分别写死结果。

3）我设定的验收红线

- 不允许用静态截图或伪代码代替可运行产品； - 不允许为了视觉效果捏造与原始数据不一致的指标； - 异常必须在原始数据中有可核对的证据； - 不得虚构已完成的测试、人工修改或部署结果（这一条我也用在了本文件的写作要求上）。

4）部署与交付细节

- 选定仓库名与公开访问形式，要求在线地址打开即进入看板； - 要求区分「在线看板链接」与「源码仓库链接」，并说明各自用途； - 要求交付包不含 node_modules、dist 等无关文件； - 要求 README 直接给出在线体验入口，且写成作品介绍而不是开发日志。

5）材料视角的纠正

我发现第一版的 AI 使用说明带有「候选人提出…」「根据候选人的需求…」这类第三人称复盘口吻，不适合直接提交，因此明确要求整份文档改为第一人称，并要求区分「我做的判断」与「AI 执行的实现」。本文件就是这个要求的产物。

5.3 关于模拟数据与静态部署的取舍

这个项目是测评场景，没有真实业务数据，也不应该使用任何真实用户信息。因此我用固定随机种子的脚本生成了一整套事件级模拟数据，好处是：

- 结果可复现，招聘方重新生成数据后看到的指标与我提交的完全一致； - 指标之间的勾稽关系真实存在（同一个用户、同一条内容能在多个页面被关联到），可以验证口径是否自洽； - 我能在数据里预先埋入几类异常，让「异常监控」这个最重要的功能可以被真实演示和核对，而不是靠截图说明。

静态部署则是为了让招聘方零成本查看作品：不需要安装环境、不需要运行命令、不需要登录。代价是没有服务端，数据只能随前端一起发布。

5.4 如果放到真实生产环境，还需要补什么

- 数据链路：把前端聚合换成服务端预聚合接口与指标层，接入真实埋点（参与、生成、审核、扫码、分享、心跳），并统一事件 ID 规范； - 实时设备状态：心跳走独立通道并做去抖动，避免网络抖动被误判为离线； - 告警与闭环：异常规则接入告警通知与工单流转（派单给技术运维或审核策略），让「发现异常 → 采取行动」真正闭环，而不是停留在看板上； - 权限与合规：运营、审核、运维的角色与数据权限分离；内容审核相关数据需要脱敏与留痕。

这些是当前版本明确没有覆盖的部分，也是我理解这个产品往下走最需要补齐的能力。
